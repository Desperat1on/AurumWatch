# 05: 事件记录与日志——近况上窗，档案落盘

**What to build:** 触发与故障警告汇成单一事件流，两处消费：主窗口事件记录区显示本次运行的最近 50 条；`logs/` 下按天写日志文件（触发、故障警告、故障出现与恢复、程序启动与退出、设置保存、配置回退、弹窗失败），自动清理 30 天前的旧文件。主窗口底部有[打开日志]按钮，在资源管理器中打开日志文件夹。日志明确不记录逐轮行情。

**Blocked by:** 02（主窗口上线）

**Status:** done

- [x] 触发或故障警告发生时，主窗口事件记录与当日日志文件同时出现同一条内容
- [x] 日志按天分文件（`logs/aurumwatch-YYYY-MM-DD.log`），启动时自动清理 30 天前的旧文件
- [x] 记录覆盖：触发、故障警告、故障出现与恢复、启动/退出、设置保存、配置回退提示、弹窗失败
- [x] 事件记录保留本次运行最近 50 条，重启即清空（与日志的分工明确：近况 vs 档案）
- [x] [打开日志] 打开日志文件夹
- [x] 不记录逐轮行情

## Comments

实现记录（2026-09-14）：

- **模块**：新增 `journal`——事件 → 文字（`alert_text`／`warning_text`／`failure_text`／`round_texts`／`line_text`）与文件命名清理（`file_name`／`file_date`／`stale_logs`／`log_dir`）是纯函数，`Journal` 是它的副作用部分（写当天的日志文件、内存里留最近 50 条记录，内部加锁）。`failures` 新增 `FailureChange` 与 `failure_changes`（照一轮前后的记账对照，得出故障的出现与恢复——不动 `update_failures` 的既有契约）；`config` 抽出 `base_dir()`（`config.json` 与 `logs/` 用同一条定位规则，见 ADR-0002）；`theme` 新增 `style_text`／`style_scrollbar`；`main_window` 新增事件记录区、[打开日志] 按钮与 `on_error`；`app` 把事件流接进 `Journal`，并补上退出记录与出错退出的调用栈。
- **一条事件两处同文**：`journal.record(text, at)` 一处写两处，整行由 `line_text` 只造一次——日志文件里的那一行与事件记录里摆的那一条**逐字相同**（测试直接比对两者）。开窗时先摆一次事件记录，启动与配置回退那几条不必等第一轮取数（ticket 02 那句「首轮取数那一段会有内容」由此兑现）。
- **事件记录摆什么**（票面、User Story 46 与 CONTEXT.md 原本口径不一，**已问过用户并定案**）：定成**与日志同一条流**——触发、故障警告、故障出现与恢复、启停、设置保存、配置回退、弹窗失败都摆上窗口，两处内容一模一样，差别只在近况留 50 条、重启即失。理由是 User Story 46 要「事件记录里有提示」，且配置回退的底部提示行只活到下一帧（实测不到 1 秒就被清掉），只落盘的话用户在窗口上看不到。`CONTEXT.md` 的「事件记录」词条已按此改写（原文只提触发与故障警告）。
- **不记逐轮行情**：`round_texts` 在没有事件时返回空元组，一轮行情一个字都不写（ADR-0003）。故障只在**出现**与**恢复**时各记一条：连续失败 12 轮只留一条「数据源故障」（实测验过）。
- **文案**（`2026-09-14 14:01:07 ` 开头的那一行）：`触发：国内金价 涨破——现价 951.24 元/克，阈值 950.00 元/克，行情时间 2026-09-14 14:01:00`／`数据源故障：国际金价 取数失败（ConnectionError: 连接被拒绝）`／`数据源恢复：国际金价 又能取到行情了（此前连续失败 1 分钟）`／`故障警告：国际金价 已连续 1 分钟取数失败（自 11:50:00 起，最近错误：…）`／`AurumWatch 启动`／`AurumWatch 退出`／`设置已保存`／`配置：<配置层给的说法>`／`弹窗显示失败：…`／`窗口出错：…`。
- **清理**：启动时清掉超过 30 天的 `aurumwatch-YYYY-MM-DD.log`；**只认自己写的格式**（`file_date` 要求 `file_name` 能把名字原样写回来），别人的文件与同名的目录一概不碰（实测：40 天前的清掉、4 天前的留着、`备注.txt` 与同名目录都留着）；边界上宁可多留一天（整 30 天的那份留着，第 31 天才清）。
- **写不进去的兜底**：日志写不进去（只读目录等）不打断监视，只在事件记录里说一句（同一件事只说一次），此后不再重试；目录每次写入前带上 `mkdir`，运行期被人删了下一件事照样落得下盘。
- **窗口那一侧**：事件记录区是只读 `tk.Text`（8 行、46 字符宽，**最新的一条在最上面**）+ 滚动条——一条触发记录折两行，一眼看得见 4 条，多的滚着看。用文本区而不是列表框，是因为故障警告把错误原文照录，列表不折行只会截掉半截。窗口最小尺寸随之从 460x320 调到 560x620（按字号缩放）：10 磅下内容实测要 607x734（未设阈值时）／596x920（四个阈值都设上时），16 磅 987x1043，20 磅 1223x1270。
- **滚动条**：`tk.Scrollbar` 在 Windows 上画的是系统那一支，配色一个都不认（红底蓝槽实测仍是浅灰）——改用 `ttk.Scrollbar` + clam 主题，深色窗口里才不至于亮一条；改外观时样式跟着重配（实测保存后 `troughcolor` 当场变成新底色）。设置窗口的字体下拉本来就切了 clam，两处同一个主题。
- **[打开日志]**：`Journal.open_dir()`（建目录 + `os.startfile`），失败就在提示行说一句。实测按钮回调传来的路径就是日志目录，且资源管理器真的打开了它（随后已关掉，没在桌面上留窗）。
- **回调异常与出错退出**：`MainWindow` 新增 `on_error`——Tk 回调里的异常既弹一次消息框，也记进事件记录与日志（`窗口出错：TypeError: …`，只记异常那一行：上屏回调 200ms 跑一次，每条都记会把日志刷爆）；启动期与运行期的致命异常在 `main()` 里把完整调用栈写进日志（消息框一闪而过，那时没有别处可看）。
- **测试**：新增 `tests/test_journal.py`（26 个：五种事件文案、一轮的顺序、按天文件名、只认自己的名字、30 天边界、两处同文、50 条上限、跨天分文件、启动清理、写不进去的兜底）；`tests/test_failures.py` 增 5 个（故障出现、持续失败不重报、恢复及时长、健康轮次无话、两个市场各报各的）。全套 161 → 193。
- **手验**（进程内驱动**真实 `app.run()`**，脚本与截图在临时目录、不入库；两段共 45 条断言全过）：
  - 第一段（假数据源：先连续失败 1 分钟，再给越线读数）——启动与两条故障出现先上窗；满 1 分钟后两条故障警告**同时**出现在事件记录与日志且逐字相同；恢复与触发各两条；事件记录里恰好九条；灌 60 条后窗口上剩 50 条（最新的「第 59 条」在最上、最早的「第 10 条」在最下、第 0～9 条只在日志里），滚轮翻得动；改外观保存后事件记录区与滚动条当场换新底色；[打开日志] 打开的是日志目录；日志一天一份、无逐轮行情。
  - 第二段（坏配置 + 必然失败的弹窗）——配置回退备份成 `config.json.bak`、又生成默认配置照常跑、两条说明在日志与事件记录里都有；两条弹窗失败（带 `RuntimeError: 造不出窗口`）同样两处同文，窗口提示行同步显示。

- **评审（2026-09-14，代码评审代理按八个角度找、再逐条独立复核，五条都带复现；前后两轮各自跑了全套与两段手验）**：
  - ① **`Journal.start()` 的清理整轮包在一个 try 里**：一份清不掉（同名目录、被占着）就把后面那些撂下——而且是**永远**撂下（挡路的不会自己消失），日志清理等于停摆。改成逐份 try：清不动的留着，其余照清。补用例（把清不掉的那份钉在中间，前后两份都要清掉；不打补丁的旧写法在这条上必挂）。
  - ② **`_report_callback_error` 一个布尔同时管消息框与日志**：第一条异常之后，**换了一条**不停出错的也再没人知道——窗口就那么冻着，哪儿也没记。改成日志按「异常那一行」记账（同一条只说一次，换一条还会记），消息框仍旧只弹第一次（对应 popup 里 `_report_sound` 的写法）。
  - ③ **`_append` 一旦写失败就永久不再写**：同步软件占一下文件（一次抖动）就把这一天的档案丢了，而窗口上看着一切正常、事后毫无痕迹。改成每条都还会试、只在头一次失败时说一句；写成功就把这句话忘掉（日后再坏还会说）。补用例（挡路的删掉后，后面的事件照样落盘）。
  - ④ **最小尺寸定在内容需求之下（560x620 vs 实测 607x788），且 pack 顺序让卡片区先占满**——拖到最小时事件记录区与底栏被挤成 1px（代理用同一套 pack 结构复现）。改成底栏与事件记录区按 `side="bottom"` **先摆**（pack 里先摆的先拿到高度）：拖小先让位的是卡片区。实测 560x620 下事件记录区仍是 8 行（234px）、三个按钮一个不少；自然尺寸 8／10／16／20 磅分别 466x684／607x788／987x1127／1223x1376，最小尺寸在各档都仍低于它。
  - ⑤ **提示行与三个按钮挤一行**：窗口一窄（或提示一长）提示被横着切掉半截、按钮被压扁（代理在原最小宽度下量到按钮与提示重叠）。改成提示**独占一行**（固定两行高、按窗口宽折行），按钮在下一行——提示来了走了窗口也不跳（行高固定）。
  - **顺手改掉的（reuse／simplify 两条轴提的）**：`failure_changes` 并回 `update_failures` 的第三个返回值（两位查找器独立指出：入参写反不会报错，只会记出一条「此前连续失败 0 秒」的假恢复——这样的 API 不该留在调用方手里）；clam 主题的切换抽成 `theme.ttk_style()` 一处并与设置窗口共用（原来是两处逐字相同的四行）；滚动条按 `Theme.scrollbar(parent, command)` 造、`paint_scrollbar()` 重涂（与 `Theme.button` 对称，`main_window` 不再拿着样式名自建控件、也不再多存一个 `_events_bar`）；写失败那句说明也走 `line_text`（记录里每一条都是「时刻 + 事由」，它不该是唯一没有时刻的）；提示行与记录改由 `_tell` 一处接线（原来「设置已保存」的字面量写了两份，[打开日志] 失败只说给窗口听、没留档）。

- **评审补轮（子代理陆续回票，逐条核对后落地；都已复现）**：
  - ⑥ **一条用例写死了 2026-09-14**：它先记事、再调 `start()`，而 `start()` 按**真实**日期清旧账——过了 30 天这条用例自己就挂（代理改时钟复现：10-14 过、10-15 挂）。改成记在「今天」，并把两边时钟一起假装成 2026-10-20 验过（29 个用例全过）。
  - ⑦ **`show_events` 每次都 `see("1.0")`**：正在往下翻旧账的人会被新来的事件拽回顶上（代理实测 yview 0.82 → 0.0），事件来得比人读得快时，旧的那些根本看不成。改成重排前先看读者停在哪儿：在最上面（或空着）就跟着新的走，翻下去了就把视线留在原处。手验加了这一条（滚到下面后新事件到了，视线没被拽走）。
  - ⑧ **`Journal._append` 只接 `OSError`**：别的异常会从 `record()` 漏出去，把取数线程整个带走（日志是旁路，不该有这个权力）。改成接 `Exception`（原因取 `strerror`，没有就取异常本身）。
  - ⑨ 出错退出的调用栈仍整段落盘，但**续行缩进四格**：一眼看出哪几行属于上一条记录，不与别的记录混作一团；`journal` 的模块说明里写明这是「一行一条」的唯一例外。
  - 三条**都是本票之前就有的、属别的票面**，记在这里做后续（未改）：`refresh_interval`／`failure_warn_minutes` 没有上限，填天文数字能存进配置、下一轮把取数线程打死（ticket 03 的校验面 + 取数线程要不要兜一层）；`config.json` 只认严格 UTF-8，记事本存成带 BOM 或 GBK 就被判成坏文件、四个阈值静默失效（`utf-8-sig` 是最小改法）；中灰底色（如 `#808080`）下警告色对比度只有 1.36:1（ticket 04 的主题派生）。
